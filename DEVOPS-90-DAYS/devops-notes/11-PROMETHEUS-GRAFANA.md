# **PART 1 – MONITORING AND OBSERVABILITY FUNDAMENTALS**

## **1. What is Monitoring?**

Monitoring is the process of continuously observing the health, availability and performance of systems, applications, servers and infrastructure.

In DevOps, monitoring helps engineers understand whether their infrastructure and applications are working correctly.

### **Example**

Imagine that you have a Linux server hosting a website.

You want to monitor:

- CPU utilization
- RAM utilization
- Disk space
- Network traffic
- Server uptime
- Application response time
- HTTP errors
- Database connections

Without monitoring, you may discover a problem only after users complain.

With monitoring, you can detect unusual behavior and investigate it earlier.

### **Why Monitoring Matters**

1.  Detect problems before customers report them.
2.  Reduce application downtime.
3.  Identify infrastructure bottlenecks.
4.  Improve application performance.
5.  Make decisions using real data.
6.  Improve incident response.
7.  Monitor infrastructure health.
8.  Measure service reliability.

**Important concept:**

Monitoring does not automatically fix problems. It provides information that helps engineers identify and resolve them.

## **2. Monitoring vs Observability**

These two concepts are related but are not exactly the same.

### **Monitoring**

Monitoring answers:

- Is the server running?
- Is CPU usage high?
- Is memory utilization increasing?
- Is the website responding?
- Is the application returning errors?

Monitoring generally focuses on predefined metrics and known failure conditions.

### **Observability**

Observability helps engineers investigate:

- Why is the application slow?
- Which service is causing a bottleneck?
- Why are requests failing?
- What happened after the latest deployment?
- Which component is responsible for increased latency?

Observability provides deeper insight into internal system behavior using telemetry data.

### **Comparison**

| **Monitoring**                | **Observability**                  |
|-------------------------------|------------------------------------|
| Tracks system health          | Helps investigate system behavior  |
| Uses predefined checks        | Supports deeper exploration        |
| Detects known problems        | Helps investigate unknown problems |
| Focuses on alerts and metrics | Uses metrics, logs and traces      |

## **3. Three Main Types of Observability Data**

### **3.1 Metrics**

Metrics are numerical measurements collected over time.

Examples:

- CPU usage: 75%
- Memory usage: 6 GB
- HTTP requests: 1,000
- Disk utilization: 80%
- Application response time: 250 ms

Prometheus primarily collects and stores metrics.

### **3.2 Logs**

Logs are records of events generated by applications and infrastructure.

Example:

    2026-11-06 10:20:15 ERROR Database connection failed
    2026-11-06 10:20:20 INFO Application restarted
    2026-11-06 10:20:25 INFO Database connection successful

Logs provide detailed information about what happened.

Grafana can visualize logs from sources such as Loki and Elasticsearch.

### **3.3 Traces**

Traces show how an individual request travels through multiple services.

Example:

    User Request
         |
         v
    API Gateway
         |
         v
    Authentication Service
         |
         v
    Order Service
         |
         v
    Database
         |
         v
    Response

Traces help identify where a request spends time and where failures occur.

### **Summary**

| **Data Type** | **Purpose**         | **Example**         |
|---------------|---------------------|---------------------|
| Metrics       | Measure performance | CPU usage           |
| Logs          | Record events       | Database errors     |
| Traces        | Follow requests     | API request journey |

**Remember:** Prometheus is primarily a metrics monitoring system. It is not a complete replacement for dedicated logging and distributed tracing systems.

# **PART 2 – PROMETHEUS FUNDAMENTALS**

## **4. What is Prometheus?**

Prometheus is an open-source monitoring and alerting toolkit designed to collect, store and query time-series metrics.

It is widely used in:

- DevOps environments
- Linux infrastructure
- Cloud infrastructure
- Docker environments
- Kubernetes clusters
- Microservices
- Application monitoring
- Database monitoring

Prometheus was originally developed at SoundCloud in 2012 and became a Cloud Native Computing Foundation (CNCF) project.

### **Simple Definition**

Prometheus collects numerical metrics from applications, servers and infrastructure, stores them with timestamps, and allows engineers to query and analyze those metrics.

### **Example**

Suppose you have three Linux servers:

    Server 1: 192.168.1.10
    Server 2: 192.168.1.11
    Server 3: 192.168.1.12

You want to monitor:

- CPU usage
- RAM usage
- Disk usage
- Network traffic

You install Node Exporter on each server.

Prometheus periodically collects metrics from these exporters and stores them.

You can then query the collected metrics and visualize them using Grafana.

## **5. Key Features of Prometheus**

### **5.1 Time-Series Database (TSDB)**

Prometheus stores metrics as time-series data.

A time series contains:

- Metric name
- Labels
- Timestamp
- Metric value

Example:

    cpu_usage{instance="server1",job="linux"} 75

Prometheus records the metric value over time.

Example:

| **Timestamp** | **CPU Usage** |
|---------------|---------------|
| 10:00         | 40%           |
| 10:01         | 55%           |
| 10:02         | 70%           |
| 10:03         | 75%           |
| 10:04         | 60%           |

This allows engineers to examine historical trends.

### **5.2 Pull-Based Architecture**

Prometheus primarily follows a pull-based monitoring model.

This means Prometheus requests metrics from monitored targets instead of requiring every target to send metrics continuously.

The process is called scraping.

Example:

    Prometheus Server
           |
           | HTTP GET /metrics
           |
           v
    Node Exporter
           |
           v
    Linux Server Metrics

Prometheus repeats this process according to the configured scrape interval.

### **5.3 PromQL**

PromQL stands for Prometheus Query Language.

It is used to retrieve, filter, calculate and aggregate metrics.

Example:

    up

This query returns the up/down status of monitored targets.

Another example:

    rate(http_requests_total[5m])

This calculates the average per-second increase in the counter over the last five minutes.

### **5.4 Multi-Dimensional Data Model**

Prometheus identifies a metric through its metric name and associated labels.

Example:

    http_requests_total{
        method="GET",
        status="200",
        instance="server1"
    }

Labels allow you to filter and group metrics.

For example:

    http_requests_total{method="GET"}

This selects metrics where the method label is GET.

**Important:** Avoid creating labels with unlimited or highly variable values, such as unique user IDs or request IDs. This can create high cardinality and excessive storage and memory usage.

### **5.5 Service Discovery**

Prometheus supports service discovery to find monitoring targets automatically.

Examples include:

- Kubernetes
- Consul
- AWS EC2
- File-based service discovery
- Static configurations

This is especially useful in dynamic environments where servers and containers are frequently created or removed.

### **5.6 Alerting**

Prometheus supports alerting rules based on PromQL expressions.

Example:

    groups:
      - name: server-alerts
        rules:
          - alert: HighCPUUsage
            expr: cpu_usage_percent > 90
            for: 5m
            labels:
              severity: critical
            annotations:
              summary: "High CPU usage detected"

This is an illustrative rule. The metric name must exist in your actual Prometheus environment.

Alertmanager can manage alert grouping, routing, silencing and notifications.

### **5.7 Scalability**

Prometheus supports techniques such as:

- Federation
- Sharding
- Remote write integrations
- External long-term storage systems

Large deployments require appropriate architecture and capacity planning. Prometheus is not automatically horizontally scalable simply by installing more servers.

## **7. Prometheus Server**

The Prometheus Server is the central component of the monitoring system.

It performs three major responsibilities:

### **Retrieval**

Retrieval is responsible for collecting metrics from targets.

Prometheus scrapes HTTP endpoints exposed by applications or exporters.

Example:

    http://192.168.1.10:9100/metrics

### **TSDB**

TSDB stands for Time-Series Database.

It stores collected metrics on disk with timestamps.

Prometheus uses its own local time-series storage engine.

### **HTTP Server**

Prometheus provides a web interface and HTTP API.

The default web interface is:

    http://localhost:9090

The server also exposes its own internal metrics.

## **8. Exporters**

An exporter is a component that exposes metrics in a format Prometheus can collect.

Some applications already expose Prometheus-compatible metrics. Other systems require exporters.

### **Common Exporters**

| **Exporter**      | **Purpose**                  | **Default Port** |
|-------------------|------------------------------|------------------|
| Node Exporter     | Linux system metrics         | 9100             |
| MySQL Exporter    | MySQL database metrics       | 9104             |
| Blackbox Exporter | Endpoint and network probing | 9115             |
| Apache Exporter   | Apache web server metrics    | 9117             |

These are common default ports; actual configurations can differ.

### **How Exporters Work**

    Linux Server
         |
         v
    Node Exporter
         |
         v
    /metrics endpoint
         |
         v
    Prometheus scrapes metrics
         |
         v
    Prometheus TSDB

## **9. Targets**

A target is an endpoint that Prometheus monitors.

Examples:

    localhost:9090
    localhost:9100
    192.168.1.10:9100
    192.168.1.11:9100

A target usually exposes metrics through an HTTP endpoint.

You can view target health from:

    http://localhost:9090/targets

## **10. Pushgateway**

Prometheus primarily uses a pull-based model.

However, some short-lived batch jobs may finish before Prometheus can scrape their metrics.

Pushgateway provides an intermediary endpoint where these jobs can publish metrics.

    Short-lived Batch Job
              |
              | Push metrics
              v
         Pushgateway
              |
              | Prometheus scrape
              v
          Prometheus

**Important:** Pushgateway is intended for specific use cases, particularly short-lived service-level batch jobs. It should not be used as a general replacement for exporters or normal Prometheus scraping.

## **11. Alertmanager**

Alertmanager receives alerts generated by Prometheus alerting rules.

Its responsibilities include:

- Grouping alerts
- Routing alerts
- Deduplicating alerts
- Silencing alerts
- Managing notification delivery

It can integrate with notification receivers such as:

- Email
- Slack
- PagerDuty
- Webhooks

## **13. Prometheus Configuration File**

Prometheus uses a YAML configuration file, normally called:

    prometheus.yml

Example:

    global:
      scrape_interval: 15s

    scrape_configs:
      - job_name: "prometheus"
        static_configs:
          - targets: ["localhost:9090"]
      - job_name: "linux-server"
        static_configs:
          - targets: ["localhost:9100"]

### **Explanation**

**global**

Contains global configuration settings.

**scrape_interval**

Defines how frequently Prometheus scrapes targets.

    scrape_interval: 15s

This means Prometheus attempts to collect metrics every 15 seconds.

**scrape_configs**

Defines the jobs and targets that Prometheus monitors.

**job_name**

Identifies a group of targets.

**static_configs**

Defines targets manually.

**targets**

Contains the hostname or IP address and port of the metrics endpoint.

### **Validate the Configuration**

Use:

``` bash
promtool check config prometheus.yml
```

This checks the Prometheus configuration syntax and structure.

After updating configuration, reload Prometheus using an appropriately configured reload mechanism or restart the service.

# **PART 6 – RUNNING PROMETHEUS WITH SYSTEMD**

## **14. What is Systemd?**

Systemd is the service manager commonly used by modern Linux distributions.

It allows you to:

- Start services
- Stop services
- Restart services
- Enable automatic startup
- Check service status
- Review service logs

Instead of manually running Prometheus every time, you can configure it as a systemd service.

### **Step 1: Create a Prometheus User**

``` bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin prometheus
```

### **Step 2: Create Directories**

``` bash
sudo mkdir -p /etc/prometheus
sudo mkdir -p /var/lib/prometheus
```

### **Step 3: Copy Prometheus Files**

For a deployment where the extracted directory is available:

``` bash
sudo cp prometheus /usr/local/bin/
sudo cp promtool /usr/local/bin/
```

Copy the configuration and console files as appropriate:

``` bash
sudo cp prometheus.yml /etc/prometheus/
sudo cp -r consoles /etc/prometheus/
sudo cp -r console_libraries /etc/prometheus/
```

### **Step 4: Set Permissions**

``` bash
sudo chown -R prometheus:prometheus /etc/prometheus
sudo chown -R prometheus:prometheus /var/lib/prometheus
sudo chown prometheus:prometheus /usr/local/bin/prometheus
sudo chown prometheus:prometheus /usr/local/bin/promtool
```

### **Step 5: Create a Systemd Service**

Create:

``` bash
sudo nano /etc/systemd/system/prometheus.service
```

Configuration:

    [Unit]
    Description=Prometheus Monitoring Server
    Documentation=https://prometheus.io/docs/introduction/overview/
    After=network-online.target
    Wants=network-online.target

    [Service]
    User=prometheus
    Group=prometheus
    Type=simple
    Restart=on-failure

    ExecStart=/usr/local/bin/prometheus \
      --config.file=/etc/prometheus/prometheus.yml \
      --storage.tsdb.path=/var/lib/prometheus \
      --storage.tsdb.retention.time=30d

    [Install]
    WantedBy=multi-user.target

### **Explanation**

| **Parameter**     | **Purpose**                      |
|-------------------|----------------------------------|
| User              | Linux account running Prometheus |
| Group             | Linux group                      |
| ExecStart         | Command used to start Prometheus |
| config.file       | Configuration file location      |
| storage.tsdb.path | Metrics database location        |
| retention.time    | How long metrics are retained    |
| Restart           | Restart behavior                 |

**Note:** The 30-day retention is an example. Actual retention should be planned based on storage capacity and monitoring requirements.

### **Step 6: Reload Systemd**

``` bash
sudo systemctl daemon-reload
```

### **Step 7: Start Prometheus**

``` bash
sudo systemctl start prometheus
```

### **Step 8: Enable Automatic Startup**

``` bash
sudo systemctl enable prometheus
```

### **Step 9: Check Service Status**

``` bash
sudo systemctl status prometheus
```

### **Useful Commands**

``` bash
sudo systemctl start prometheus
sudo systemctl stop prometheus
sudo systemctl restart prometheus
sudo systemctl enable prometheus
sudo systemctl disable prometheus
sudo systemctl status prometheus
```

### **View Logs**

``` bash
sudo journalctl -u prometheus -f
```

# **PART 8 – PROMQL**

## **19. What is PromQL?**

PromQL stands for Prometheus Query Language.

It is used to retrieve and process time-series data stored in Prometheus.

PromQL can:

- Select metrics
- Filter metrics using labels
- Calculate rates
- Aggregate data
- Compare values
- Calculate averages
- Analyze historical metrics

### **Where to Execute PromQL?**

Open:

    http://localhost:9090/graph

Enter a query and click Execute.

## **20. Basic PromQL Queries**

### **Query 1: Check Target Status**

    up

Results:

- `1` = Target is up.
- `0` = Target is down.

### **Query 2: Select a Metric**

    node_memory_MemAvailable_bytes

Returns available memory in bytes for monitored Node Exporter instances.

### **Query 3: Filter by Job**

    up{job="node-exporter"}

Returns the health status of targets belonging to the specified job.

### **Query 4: Filter by Instance**

    up{instance="localhost:9100"}

### **Query 5: Count Targets**

    count(up)

### **Query 6: Calculate Total HTTP Requests**

    sum(http_requests_total)

This example works only if the application exposes this metric.

## **21. Useful PromQL Functions**

### **rate()**

Calculates the average per-second increase of a counter over a specified range.

Example:

    rate(http_requests_total[5m])

### **increase()**

Calculates the total increase of a counter over a specified time range.

    increase(http_requests_total[1h])

### **sum()**

Adds values together.

    sum(up)

### **avg()**

Calculates an average.

    avg(up)

### **max()**

Returns the maximum value.

    max(up)

### **min()**

Returns the minimum value.

    min(up)

### **count()**

Counts the number of returned time series.

    count(up)

## **22. Example Linux Monitoring Queries**

### **CPU Usage Percentage**

    100 * (1 - avg by(instance) (
      rate(node_cpu_seconds_total{mode="idle"}[5m])
    ))

This calculates non-idle CPU time as a percentage.

### **Memory Usage Percentage**

    100 * (
      1 -
      node_memory_MemAvailable_bytes /
      node_memory_MemTotal_bytes
    )

### **Disk Usage Percentage**

    100 * (
      1 -
      node_filesystem_avail_bytes{
        mountpoint="/",
        fstype!=""
      } /
      node_filesystem_size_bytes{
        mountpoint="/",
        fstype!=""
      }
    )

### **Network Received Bytes Per Second**

    rate(node_network_receive_bytes_total[5m])

### **Network Transmitted Bytes Per Second**

    rate(node_network_transmit_bytes_total[5m])

### **Server Uptime**

    time() - node_boot_time_seconds

These queries assume that the relevant Node Exporter metrics are available and that the target labels match your environment.

## **48. Python Custom Exporter Example**

Install dependencies:

``` bash
pip install prometheus-client psutil
```

Example:

    from prometheus_client import start_http_server, Gauge
    import psutil
    import time

    # Gauge stores a value that can increase or decrease.
    firefox_memory_percentage = Gauge(
        "firefox_memory_percentage",
        "Firefox memory usage percentage"
    )

    def collect_metrics():
        for process in psutil.process_iter(["name", "memory_percent"]):
            try:
                process_name = process.info["name"] or ""

                if "firefox" in process_name.lower():
                    memory = process.info["memory_percent"]

                    if memory is not None:
                        firefox_memory_percentage.set(memory)

            except (psutil.NoSuchProcess, psutil.AccessDenied):
                continue

    if __name__ == "__main__":
        # Expose metrics on port 8888.
        start_http_server(8888)

        while True:
            collect_metrics()
            time.sleep(15)

``` yaml
    - targets: ["localhost:8888"]
```

# **PART 18 – PROMETHEUS METRIC TYPES**

## **49. Four Main Metric Types**

Prometheus commonly uses four metric types:

1.  Counter
2.  Gauge
3.  Histogram
4.  Summary

## **50. Counter**

A Counter is a cumulative metric that normally only increases.

It can reset when the monitored process restarts.

Examples:

- Total HTTP requests
- Total failed requests
- Total completed jobs
- Total processed messages

Example:

    http_requests_total 1500

Use `rate()` to calculate the per-second increase.

    rate(http_requests_total[5m])

## **51. Gauge**

A Gauge represents a value that can increase or decrease.

Examples:

- CPU usage
- Memory usage
- Number of active connections
- Queue size
- Temperature

Example:

    application_memory_usage_bytes 524288000

## **52. Histogram**

A Histogram groups observations into configurable buckets.

It is commonly used for:

- Request duration
- Response size
- Database query duration

For example, request durations can be grouped into buckets:

    0.1 seconds
    0.5 seconds
    1 second
    2 seconds
    5 seconds

A Histogram exposes bucket counts, a total observation count and a sum.

Example metrics:

    http_request_duration_seconds_bucket
    http_request_duration_seconds_sum
    http_request_duration_seconds_count

You can calculate a percentile using `histogram_quantile()`.

Example:

    histogram_quantile(
      0.95,
      sum by (le) (
        rate(http_request_duration_seconds_bucket[5m])
      )
    )

This calculates an estimated 95th-percentile request duration across the selected series.

## **53. Summary**

A Summary tracks observations and exposes a count, sum and configured quantiles.

It is useful for analyzing distributions within an individual instrumented process.

Unlike Histogram buckets, Summary quantiles generally cannot be meaningfully aggregated across multiple application instances.

### **Comparison**

| **Metric Type** | **Behavior**                      | **Example**       |
|-----------------|-----------------------------------|-------------------|
| Counter         | Increases cumulatively            | Total requests    |
| Gauge           | Goes up and down                  | CPU usage         |
| Histogram       | Counts observations in buckets    | Request duration  |
| Summary         | Calculates observation statistics | Latency quantiles |

## **60. PodMonitor**

PodMonitor is a Kubernetes custom resource provided by Prometheus Operator.

It selects pods using labels and specifies which pod endpoints expose metrics.

Illustrative structure:

``` yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: application-monitor
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: my-application
  podMetricsEndpoints:
    - port: metrics
      path: /metrics
      interval: 15s
```

This example assumes:

- The application pods have the label `app: my-application`.
- The pod exposes a named port called `metrics`.
- The Prometheus Operator is installed.
- Prometheus is configured to select this PodMonitor.

## **61. ServiceMonitor**

ServiceMonitor is another Prometheus Operator custom resource.

It discovers metrics endpoints through Kubernetes Services.

Example:

``` yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: application-service-monitor
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: my-application
  endpoints:
    - port: metrics
      path: /metrics
      interval: 15s
```

The selector must match the labels on the Service, and the port must refer to the correct named Service port.

### **PodMonitor vs ServiceMonitor**

| **PodMonitor**                     | **ServiceMonitor**                 |
|------------------------------------|------------------------------------|
| Selects pods directly              | Selects Kubernetes Services        |
| Useful for pod endpoint monitoring | Useful for service-based discovery |
| Uses pod labels                    | Uses service labels                |

# **PART 23 – ADVANCED PROMETHEUS CONCEPTS**

## **73. Recording Rules**

Recording rules allow Prometheus to precompute frequently used or expensive queries.

Instead of repeatedly evaluating a complex expression, Prometheus calculates the result periodically and stores it as a new time series.

Example:

    groups:
      - name: application-recording-rules
        interval: 30s
        rules:
          - record: job:http_requests:rate5m
            expr: sum by(job) (
              rate(http_requests_total[5m])
            )

You can then query:

    job:http_requests:rate5m

Benefits:

- Faster dashboards
- Simplified queries
- Reduced repeated computation

## **74. Blackbox Monitoring**

Blackbox monitoring tests a system from the outside without requiring access to its internal implementation.

Examples:

## **75. Whitebox Monitoring**

Whitebox monitoring observes the internal state of an application or infrastructure component.

9.  Monitor target health.
10. Document exporters and their configuration.
11. Plan storage capacity.
12. Secure the metrics endpoints.

## **80. Grafana Best Practices**

1.  Keep dashboards simple.
2.  Focus on important metrics.
3.  Use meaningful panel titles.
4.  Use correct units.
5.  Use consistent colors.
6.  Avoid unnecessary panels.
7.  Use variables for reusable dashboards.
8.  Add annotations for deployments and incidents.
9.  Use actionable alerts.
10. Review dashboards regularly.

## **81. Alerting Best Practices**

Avoid alert fatigue.

An alert should indicate something that requires investigation or action.

Good alert design includes:

- Clear severity levels
- Appropriate thresholds
- Evaluation periods
- Useful descriptions
- Relevant notification routing
- Links to dashboards or runbooks

Alert on meaningful symptoms, not every small metric fluctuation.

# **PART 25 – SECURITY CONSIDERATIONS**

## **82. Securing Prometheus**

Prometheus endpoints should not automatically be considered safe for public exposure.

Important measures:

- Restrict access through firewalls.
- Use private networks where appropriate.
- Configure authentication and authorization through suitable components.
- Use TLS where required.
- Limit access to sensitive metrics.
- Keep software updated.
- Review access to administrative endpoints.

## **83. Securing Grafana**

Recommended measures:

- Change default credentials.
- Use strong passwords.
- Configure appropriate user roles.
- Enable HTTPS.
- Restrict public access.
- Keep plugins updated.
- Avoid exposing sensitive dashboard information.
- Back up important configuration and dashboards.

## **84. Protecting Exporters**

Exporters can expose sensitive infrastructure details.

Recommended measures:

- Bind to appropriate network interfaces.
- Restrict inbound connections.
- Allow scraping only from trusted Prometheus servers.
- Use authentication and TLS where supported and required.
- Run exporters with dedicated low-privilege users.
- Avoid exposing metrics endpoints to the public internet.

## **85. Data Privacy**

Monitoring data can reveal:

- Infrastructure details
- Application behavior
- Internal hostnames
- Service names
- User-related operational information

Avoid collecting sensitive personal information unnecessarily.

# **PART 30 – COMMON INTERVIEW QUESTIONS AND ANSWERS**

## **Q1. What is Prometheus?**

Prometheus is an open-source monitoring and alerting toolkit that collects and stores time-series metrics.

## **Q2. What is Grafana?**

Grafana is an open-source visualization and analytics platform used to create dashboards from different data sources.

## **Q3. What is the difference between Prometheus and Grafana?**

Prometheus collects and stores metrics. Grafana visualizes data from Prometheus and other supported data sources.

## **Q4. What is PromQL?**

PromQL is the query language used to retrieve and analyze Prometheus metrics.

## **Q5. What is a time-series database?**

A database that stores data points associated with timestamps, allowing values to be analyzed over time.

## **Q6. What is an exporter?**

An exporter exposes metrics from a system or application so that Prometheus can scrape them.

## **Q7. What is Node Exporter?**

Node Exporter exposes Linux system metrics such as CPU, memory, disk and network information.

## **Q8. What is the default Prometheus port?**

## **Q9. What is the default Grafana port?**

## **Q10. What is the default Node Exporter port?**

## **Q11. What is a scrape interval?**

The interval between successive attempts by Prometheus to collect metrics from a target.

## **Q12. What is a target?**

An endpoint monitored by Prometheus.

## **Q13. What is a job?**

A group of monitoring targets defined under a Prometheus scrape configuration.

## **Q14. What is a label?**

A key-value pair attached to a metric to provide additional information and filtering dimensions.

## **Q15. What is Alertmanager?**

Alertmanager manages Prometheus alerts, including grouping, routing, deduplication and notification delivery.

## **Q16. What is Pushgateway?**

Pushgateway provides an intermediary endpoint for short-lived jobs to publish metrics for Prometheus to scrape.

## **Q17. What is the difference between Counter and Gauge?**

Counter normally increases cumulatively. Gauge can increase and decrease.

## **Q18. What is a Histogram?**

A metric type that groups observations into buckets and exposes their counts and sums.

## **Q19. What is a Summary?**

A metric type that exposes observation counts, sums and configured quantiles.

## **Q20. What is Service Discovery?**

A mechanism through which Prometheus automatically finds monitoring targets.

## **Q21. What is PodMonitor?**

A Prometheus Operator resource that discovers metrics endpoints on selected Kubernetes pods.

## **Q22. What is ServiceMonitor?**

A Prometheus Operator resource that discovers metrics endpoints through selected Kubernetes Services.

## **Q23. What is the difference between Blackbox and Whitebox monitoring?**

Blackbox monitoring tests externally observable behavior. Whitebox monitoring examines internal system metrics.

## **Q24. What is a recording rule?**

A rule that periodically calculates and stores the result of a PromQL expression.

## **Q25. Can Grafana monitor multiple data sources?**

Yes. Grafana supports multiple data sources, including Prometheus, Loki, Elasticsearch and databases.

## **Q26. Why do Prometheus targets show DOWN?**

Possible reasons include exporter failure, incorrect IP or port, network connectivity issues, firewall restrictions or incorrect metrics paths.

## **Q27. What is kube-prometheus-stack?**

A Helm chart that packages Prometheus Operator-based Kubernetes monitoring components.

## **Q28. How can Jenkins be monitored using Prometheus?**

A compatible Jenkins Prometheus plugin or another metrics integration can expose metrics that Prometheus scrapes and Grafana visualizes.

## **Q29. What is high cardinality?**

High cardinality occurs when a metric has too many distinct label combinations, potentially increasing Prometheus memory and storage requirements.

## **Q30. What is the relationship between metrics, logs and traces?**

Metrics measure system behavior, logs record events, and traces follow requests through distributed systems.
